# 2026-10-05 最初の題材: テーマ・言語の切り替えサイト

#13 で決めたこと。Command の仕様は [apps/settings/docs/commands.md](../../apps/settings/docs/commands.md)。

## 題材をテーマ・言語の切り替えにした理由

* 最初は「ボタンを押すだけのサイト」を考えたが、味気ないため、どのサイトにもある「表示設定」にした
* 言語の切り替えで i18n の仕組みを作れ、「英語にしてダークにして」が 1 バッチ・Undo 1 回で戻る例を見せられる
* リセットに `requiresConfirmation` を付け、AI からの操作の確認を見せる

## 言語の切り替えボタンを出した理由

* 「画面にボタンはないが AI に頼めばできる操作」として、言語の切り替えをボタンなしにする案もあった
* チャット（#11）がない今は、普通の人が AI に頼む手段がなく試せない。この見せ方は No UI サイト（#14）で扱う

## i18n を自前の辞書にした理由

* 文言が 20 程度で、ライブラリ（i18next など）を入れるほどではない
* 日本語の辞書のキーから型を作り、英語の辞書に同じキーがなければ型エラーにする
* 最初は操作の記録・確認ダイアログのために Command を人向けの文に直していた（`describe-command.ts`）。操作の記録を外し、確認が要るのはリセットだけなので、確認ダイアログは固定の文言にした

## 確認ダイアログのつなぎ方

* `confirm` は Promise を返す関数なので、「確認待ち」を持つ小さなストア（`confirm-bridge.ts`）を作り、`AlertDialog` から答える
* 確認待ちの間に次の確認が来たら、前のものは拒否する
* ダイアログを開いたときは「やめる」にフォーカスする（Radix の既定。安全側）

## 動作確認の方法

* このセッションでは chrome-devtools MCP が読み込まれていなかったため、手元の Chrome を Playwright（作業用ディレクトリに一時的に入れたもの）で動かして確認した
* 本物の WebMCP（`document.modelContext`）は Chrome のフラグが必要で、今回は確認していない。開発中だけ `window.__aiTools` に同じツールを出し、そこから AI の操作を試した

## レビューを受けて画面を作り直した（PR #18）

* 最初の版は、ページに「ボタンでも AI でも変えられる」「WebMCP が使えます」といった説明、操作の記録、元に戻す / やり直すを載せていた
* 「サイトはあくまで一般的なサイト」「仕組みの説明は別でする」「AI からの操作の本命はチャット」とのレビューを受け、説明を外し、ヘッダーと見出しだけのページにした
* 操作の記録はチャットのボタンからダイアログで出し、元に戻す / やり直すはチャットから頼む形にする（#11 に追記）
* リセットのボタンも外し、`reset_settings` は AI からだけ実行できる操作として残した（「画面にない操作」の例にもなる）

## React の書き方を一般的な形に寄せた（PR #18 のレビュー）

* 最初は `useSyncExternalStore` でセッションを直接購読し、`main.tsx` でセッションを作っていた
* 「見慣れない」「実際のサービスに近い形に」というレビューを受け、`SettingsProvider`（Context）でセッションを作り、`useState` / `useEffect` で購読する形にした。画面からは `useTheme` / `useI18n` だけを使う
* Provider は好みが分かれるが、状態管理のライブラリを足すよりはよいと判断した
* `.dark` と `lang` を `<html>` に反映するのは Provider の 1 か所だけにした（next-themes などと同じ形）。フックは読み書きだけを持つ
* AI 向けツールの登録は Provider の `useEffect` で行い、アンマウントで解除する
* docs はサンプル単体で読めるよう、monorepo の docs へのリンクに頼らない書き方にした
* さらにレビューを受け、セッション（AI もここを通る）はサイト全体の話なので、設定の機能から切り離した。Next.js のような構成にし、`layout/`・`pages/<ページ>/`（普通のサイトの部分）と `session/`（サイト全体の土台）をフォルダで分けた
* 次の題材は、別アプリではなくこのサイトにページを増やす形も検討する（#13 のマージ後に相談）

## 普通のサイト + Command の層に組み替えた（2026-10-06・PR #18 のレビュー）

* ここまでは状態の持ち主が Command のセッションで、`useTheme` / `useI18n` が `useSession()` を呼んでいた。画面のボタンも `session.execute(…)` を通っていた
* 「普通のサイトに **足す** 形にしたい」「session / Command がなくてもサイトとして成立させたい」「`language` / `setLanguage` などを Command に当てはめる向きにしたい」というレビューを受け、依存の向きを逆にした
  * 設定は `SettingsProvider` の `useState` で持ち、ボタンは `setTheme` / `setLanguage` を直接呼ぶ
  * Command の層（`session/`）は、`useTheme` / `useI18n` の値と setter を `store` にして、セッションにつなぐ（`use-site-store.ts`）。セッションの `store` は #19 で基盤に足した
  * Command の定義も `session/` に移し、`settings/` は `@ai-friendly/command` を参照しないようにした
* `SessionProvider` と `ConfirmDialog` を外してもサイトが動くことを、実際に外して確かめた
* これに合わせて、CLAUDE.md の「状態の変更は必ず Command を通す（UI も）」を「サイトは Command なしで成立させ、AI の操作だけ Command を通す」に改めた
* Undo / Redo は基盤から外した（#21）。上の「Undo 1 回で戻る例」は見せない

## AI の層を最小限にした（2026-10-06・PR #18 のレビュー）

* 組み替えの後も `session/` にファイルが 8 つあり、「session」という言葉もわかりにくかった
* 確認ダイアログを普通のサイトの部品にした（`confirm/` の `useConfirm`）。`await confirm(…)` ではい / いいえ が返るので、AI 以外の処理でも使える。AI の層は確認が要るときにこれを呼ぶだけ
  * 文言は辞書のキーで渡し、ダイアログの側で訳す。確認中に言語が変わっても追従し、AI の層が最新の `t` を持ち回らずに済む
* Command を `commands/` に分けた。Command が増えたときに、どこに足すかがすぐわかる
* 残りを `ai/` にまとめ、`<Ai />`（描画しない部品）と `use-site-store.ts` の 2 ファイルにした。`useSession()` は使う画面がないので消した（チャット #11 で必要になったら足す）
* 名前は「session」より、何のためのものかがすぐわかる「Ai」にした。`app.tsx` の `<Ai />` を外せば、AI から操作できなくなるだけでサイトは動く
* 言語名（JA / 日本語）は、表示中の言語に関係なくその言語で書くので、辞書ではなく `i18n/language-names.ts` に置いた
