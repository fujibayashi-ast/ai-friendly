# 2026-10-06 LLM の切り替えと Gemini Nano

#29 で決めたこと。仕様は [docs/assistant.md](../assistant.md) の「プロバイダ」。

## ローカル LLM は Prompt API と WebLLM の両方、Prompt API を先に

| | Chrome の Prompt API（Gemini Nano） | WebLLM（Qwen3.5-4B） |
| --- | --- | --- |
| ライブラリ | 不要（Chrome に入っている） | `@mlc-ai/web-llm`。Worker で動かす |
| 使えるブラウザ | パソコン版の Chrome 148 以降。ディスク 22 GB・メモリ 16 GB などの条件あり | WebGPU が使えるブラウザ。メモリ 16 GB 程度 |
| ダウンロード | Chrome が 1 回だけ。サイトをまたいで共有される | サイトごとに約 2.4 GB |
| ツールの呼び出し | 返事の形を JSON Schema で縛れる | 手書きの形で出させる。daw-tool の測定で、Command 1〜2 個の操作ならできた |

* 両方入れる。使えるブラウザが違うため
* 1 PR にまとめると大きいので、切り替えの作りと、ライブラリの要らない Prompt API を先にした。WebLLM は #32

## ツールの呼び出しは `responseConstraint` で受ける

* Prompt API には `tools`（ブラウザがツールを実行する仕組み）の案があるが、使わなかった
  * Chrome での提供状況がはっきりしない
  * 実行がブラウザの中で完結し、`runChat` の「検証 → 確認 → `run`」・ツールの行の表示に乗せにくい
* 代わりに、返事を `{ calls, reply }` の JSON にし、`responseConstraint`（JSON Schema）で形を縛った。`calls` はツールごとの `inputSchema` の `anyOf` なので、存在しないツール・形の違う引数は出せない
* 結果は user の発言（`Result of <tool>: ...`）として返す。Prompt API の役は system / user / assistant だけのため
* 小さいモデル向けに、ツールの一覧（名前と説明を 1 行ずつ）をシステムプロンプトに載せた。#29 の「`describeCommands` を載せるか」はこれで対応した（`AiTool` の `name` / `description` から作るので、`describeCommands` は使わない）

## 手元の Gemini Nano で試して直したこと

* 最初は返事を `{ calls, reply }` の 1 つの形にしていたが、ツールを呼ぶと同時に「設定しました」と返事を書き、結果を見た後にも同じツールを呼び直した
  * 返事の形を「`{ calls }` か `{ reply }` のどちらか一方」にした（`anyOf`）
  * ツールの結果のすぐ後に「結果を踏まえて返事する（まだ必要なツールがあるときだけ呼ぶ）」と 1 行添えた。システムプロンプトより、近くに書くほうが小さいモデルは従いやすい
* 「英語にして」を、自分の返事の言語のことだと受け取り、ツールを呼ばなかった
  * settings サイトのツールの説明を、何の設定かがわかるようにした（"Change the language this website is shown in (ja: Japanese, en: English)."）
  * システムプロンプトに「『ダークにして』『英語にして』のような頼みはサイトのことなのでツールを使う」と足した

  * それでも主語のない「英語にして」は取り違えやすく、「サイトを英語にして」なら通った。話しかけ方の例を「サイトを英語にして」（en: "Show this site in Japanese"）にした
* 引数のない `reset_settings` に `"confirm": true` を足して呼び、検証で失敗した（説明の「[asks the user to confirm]」を見て足したとみられる）
  * `responseConstraint` の引数のスキーマに `additionalProperties: false` を足し、知らない項目を出せないようにした（Command の検証は知らない項目をはじくので、それに合わせる）

## セッションは返事のたびに作る

* `ChatProvider` は会話をまるごと受け取る形なので、それに合わせて返事のたびにセッションを作り、`destroy()` する
* セッションを持ち越す・事前に読み込む（pre-warm）と速くなるが、最小限のため入れなかった

## 切り替えは候補の一覧を渡す

* `Chat` / `FloatingChat` の `provider` / `setup` を `providers`（`{ label, provider?, setup? }` の一覧）にした
* どれを出すか・キーの保管・システムプロンプトはサイトが決め、どれを選んでいるかはチャットが持つ
* #30 の作業中は `label` をプロバイダに持たせる案だったが、キーがなくて `provider` がまだないときも名前が要るので、候補に持たせた。`id` は持たない
* 部品は shadcn の `Select`。一覧はボタンの上に開く（入力欄の下に置くため）
* 「キーを変更」は見出しに置いたまま。Gemini Nano を選んでいても出るが、押しても Claude のキーが消えるだけなので、最小限としてこのままにした

## 確かめられたこと・確かめられなかったこと

* Claude Code が Playwright で動かす Chrome では、`LanguageModel.availability()` が `"unavailable"` だった（使い捨てのプロフィールのため）。画面の流れは `LanguageModel` を差し替えて確かめた
* 本物の Gemini Nano でツールを呼べるかは、手元の Chrome（`"available"`）で確かめる

## WebLLM（Qwen3.5 4B）を足した（#32）

* Gemini Nano と同じ「`{ calls }` か `{ reply }`」の JSON で受け取る。WebLLM の `response_format: { type: "json_object", schema }` で同じ JSON Schema を使えるので、システムプロンプト・返事の形・会話の変換・返事の読み取りを `providers/json-tools.ts` に切り出して共有した
* ライブラリは `@mlc-ai/web-llm`（0.2.85）。ブラウザで Qwen を動かすのに必要。押したときに動的 import し、推論は Web Worker で動かす。選ばない人の最初の読み込みは 459 KB → 463 KB（WebLLM 本体の約 5.9 MB は別のチャンク）
* モデルは daw-tool の測定で動いた `Qwen3.5-4B-q4f16_1-MLC` に固定した
* 思考モードは `extra_body: { enable_thinking: false }` で止めた（daw-tool の手書きの形では ` /no_think` も要ったが、JSON Schema で縛るので考え始める余地がない）
  * ただし Qwen3.5 は、それでも JSON の前に空の `<think>\n\n</think>` を書く。最初はこれで `JSON.parse` に失敗し、すべての返事が「返事を受け取れませんでした」になった。先頭の `<think>...</think>` を取り除いてから読むようにした
* 既定のサンプリングでは、返事の日本語にほかの言語の単語が混ざった（「workplaceのテーマを」「enregistré.」など）。`temperature: 0` にするとほぼ直った
* プランでは「キャッシュにあれば『モデルを読み込む』、なければ『モデルをダウンロード』」と出し分ける予定だったが、キャッシュを確かめるには WebLLM 本体をページを開いた時点で読み込む必要があるため、「モデルを読み込む」の 1 つにして、注記に「初回だけ約 2.4 GB をダウンロード」と書いた
* ページを開いただけでは読み込まない。GPU のメモリを使うので、押したときだけにした

| --- | --- | --- |

## 候補の書き方を揃えた（#39）

* #33 のレビューで、Claude だけその場でオブジェクトを書き、Gemini Nano・Qwen はフックの結果を渡していて書き方が揃っていない、と指摘があった。3 つそろってから揃えることにした
* Claude も `useClaude` にし、`providers={[claude, geminiNano, qwen]}` と並べる形にした。キーはサイトから `apiKey` / `onApiKeyChange` で受け取る（持ち方はサイトが決める）
* 「キーを変更」は、`FloatingChat` の見出し（`actions`）から、候補ごとの `actions` に移した。Claude を選んでいるときだけ、入力欄の左下（切り替えの隣）に出る。見出しに置いたままにするには、どの候補を選んでいるかを `Chat` から `FloatingChat` に持ち上げる必要があるため
* `FloatingChat` の `actions` は使うものがなくなったので外した


## 失敗したのに「できました」と返事をした（#68）

* ネットショップで、Qwen3.5 4B が `set_cart_quantity` の失敗（`product "6" is not in the cart`）のあとに「カートに 2 個追加しました」と返事をした。カートは空のまま。同じ頼みで 5 回中 5 回（temperature 0）
* 結果の後に毎回「結果を踏まえて返事する」とだけ添えていて、失敗の結果を読まずに、頼みが済んだ前提で返事を作っていた
* 最後の呼び出しの結果に失敗があるときだけ、添える 1 行を変えた（成功のときのプロンプトは今までと同じ長さ）

| 結果 | 添える 1 行 |
| --- | --- |
| 失敗がある | `A tool failed (see "ok": false). Do not say it succeeded. Tell the user in their language what could not be done and why.` |
| 確認で拒否された | `The user declined. Do not call it again; tell the user in their language that it was not done.` |

* 比べた案: 失敗のときに「理由を見て直して呼び直すか、できなかったことを伝える」と書く
  * 採らなかった理由: Qwen は呼び直しを優先し、頼みに合わない呼び直しまでした（空のカートで「マグカップを 1 つ減らして」→ `add_to_cart` で 1 つ入れて「追加しました」）。呼び直しを勧めなくても、直せる失敗は自分から呼び直した（「はちみつを買えるだけ」→ `add_to_cart`）
* 拒否を分けたのは、「呼び直す」と読めると、拒否された操作をまた呼んで確認ダイアログがまた出るため
