# 2026-10-07 守りをサイトの関数に置き、結果を多めに返す

#83・#84 で決めたこと。ルールは CLAUDE.md の Domain Rules と [docs/commands.md](../commands.md) の「持たないもの」。

## きっかけ

* 予約フォーム（PR #81）のレビューで、`submit_reservation` の `run` が画面の「予約する」と別に検証を書いていた。画面と同じ `submit()` を呼んで、結果を英文にするだけに直した
* ネットショップ（PR #65）では、ボタンの disabled だけでなく、注文の送信中の守りをサイトの関数にも入れた
* コンセプトは「普通のサイトに AI を足す」。画面から呼ばれても AI から呼ばれても、挙動が一致するのが理想
* 見直すと、ネットショップのカートと予約の `show_availability` は、「なぜだめか」を Command が自分で判定していた。サイトの関数は同じ場合に黙って何もしない（または在庫までにそろえる）。画面ではボタンが押せないので食い違わないが、判定が 2 か所にあった

## 決めたこと

* 画面と Command は同じサイトの関数を呼ぶ。守り（処理中は受け付けない・入力のルール・在庫など）はサイトの関数に置く
* サイトの関数は結果を多めに返す（だめな理由・予約番号・注文番号・足りない項目）。画面と Command は、それぞれ要るものを使う。画面は使わなくてよい
* Command は結果を AI 向けの短い英文にするだけ。状態の丸ごとは `get_state` で読む
* 画面に同じ操作がないもの（まとめて入れる `fill_reservation_form`）は、Command 側に処理があってよい

## そろえたところ

| 題材 | 前 | 後 |
| --- | --- | --- |
| ネットショップのカート | Command が `busy` / `checkStock` / `notInCart` で先に判定。`shop.ts` は在庫を超える数を黙って在庫までにそろえる | `shop.ts` の `addToCartError` などが理由を返し、`useShop` の関数が `{ ok, error }` を返す。在庫を超える数は断る |
| ネットショップの注文 | Command が送信中・空のカートを判定 | `orderError` が判定し、`placeOrder` が注文番号か理由を返す。`place_order` は成功で `order 1001 was placed` |
| 予約の週 | Command が「今週より前」を判定。`showWeek` は日付の形だけ見る | `weekError` を `showWeek`・カレンダーの「前の週」・Command が使う |

* 判定は今の描画の state で行い、変更は `setState(s => …)` で最新の state に重ねる。AI が 1 回の返事で続けてカートに入れても、片方が消えないように
  * 続けて呼ばれたとき、2 回目の判定は 1 回目の変更を見ていない（描画の前なので）。2 回目が在庫を超えるときは、結果が `ok` でも `setState` の中で何もしないことがある。前（Command が判定）も同じで、`ref` で最新を持たないことにしたので（PR #66）そのままにする

## 比べた案

| 案 | 採らなかった理由 |
| --- | --- |
| 判定は Command に残し、サイトの関数は黙って何もしない | 判定が 2 か所になり、片方だけ直すと画面と AI で挙動がずれる |
| `setState(result.state)` で、判定した state をそのまま入れる | 続けて呼ばれたとき、2 回目が 1 回目の変更を上書きして消す |
| 在庫を超える数は今までどおり在庫までにそろえ、そろえたことを返す | 「3 個入れて」で 2 個しか入らないのを黙って進めるより、断って AI がユーザーに伝える方がわかりやすい。画面では在庫で押せなくなるので変わらない |

## 気づいたこと

* AI を足すと、画面とは別の呼び出し元ができる。Command に同じ判定を書き写したくなったら、そこがサイトの関数に置くべき場所の目印になる
* 画面だけなら disabled で済ませがちな守りや、返り値を使わない結果も、サイトの関数に持たせることになる。新しく求められるものではなく、普通の良い設計（どこから呼んでも同じ結果）を AI の層が思い出させる
