# 2026-10-05 AI 向けツールの置き場所と粒度

#9 で決めたこと。仕様は [docs/ai-tools.md](../ai-tools.md)。

## ツールと WebMCP 登録を `command` に置いた理由

* 当初は `assistant` に「AI 側一式」（ツール生成・WebMCP 登録・LLM・チャット UI）をまとめる予定だった
* ツール生成と WebMCP 登録は Command の定義を読み替えるだけで、重い依存（React・LLM）がない
* 「チャットを使わず WebMCP だけで操作される場合も `command` 単体で成立させる」方針と、WebMCP 登録が `assistant` にあることが食い違っていた
* `assistant` は「サイト内の AI チャット」（チャット UI と LLM プロバイダの切り替え）に絞った（#11）
* WebMCP は LLM プロバイダの選択肢ではない（AI がサイトの外にいる）。チャットと WebMCP は同じツールを使う別の入口として扱う
* WebMCP の仕様はまだ変わるため、登録まわりはサブパス `@ai-friendly/command/webmcp` に分けた

## ツールを 3 種類にした理由

* WebMCP のガイドは「ツールは atomic で組み合わせられるように」を勧めており、Command ごとのツールで引数の型（`inputSchema`）を正確に伝える
* このプロジェクトの見せどころは「まとめて実行・全部か無しか・Undo 1 回」なので、`execute_commands`（バッチ）も用意した
* 小さいローカル LLM は、ツールの説明（JSON Schema）が長いとつまずく。daw-tool #250 では 1 Command 1 行の短い一覧の方が成績が良かった。チャットには短い一覧を載せた `execute_commands` と `get_state` だけを渡す想定
* AI が ID を知るために `get_state` を用意した。状態の全部を渡すとトークンが増えるため、見せ方はアプリが `describeState` で決める

## 短い一覧を zod の JSON Schema から作る理由

* zod の定義を直接たどるより、`z.toJSONSchema(args, { io: "input" })` の結果をたどる方が、zod の内部の形に依存しない
* `io: "input"` にすると、`default` のある項目を省略できる項目として扱える
