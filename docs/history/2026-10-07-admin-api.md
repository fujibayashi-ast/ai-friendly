# 2026-10-07 管理画面のデータをダミーの API から取る（TanStack Query）

#97 で決めたこと。仕様は [apps/admin/docs/commands.md](../../apps/admin/docs/commands.md)。

## きっかけ

* 管理画面（#73）は、ダミーデータを全部 Provider の `useState` に持ち、`get_state` では画面と同じ絞り込みをかけて「見えている行だけ」を再現していた（`page-state.ts`）
* レビューで「AI 用にしては大げさでは」と話すうちに、本物のサイトでは、ページを開いたときに API からそのページの分だけを取るので、手元には表示している分しかなく、`get_state` も自然に表示と一致する、と気づいた
* 読者が自分のサイトに当てはめやすいよう、データの取り方を本物に近づける

## 決めたこと

* ダミーの API（`admin-api.ts`）を置き、そのページの分だけを返す（通信せず 0.3 秒待つ）。データはモジュールの中に持つ（サーバーの役）
* だめな理由（存在しない・発送済み・在庫の範囲）は API が判定し、`ApiError` で断る。ネットショップで「二重の注文は API の役目」とした（#66）のと同じく、本物ではサーバーの役目。判定のルールは前の `admin.ts` をサーバーの役で使う
* TanStack Query で持つ。キーと取得（`ordersQuery` など）・mutation（`useShipOrder` など）を `queries.ts` に置き、画面と AI の層が共有する
  * ページ遷移の Command は、ページと同じキーで `fetchQuery` を待ってから結果を返す。取得はページの `useQuery` と共有され、二重に取らない
  * `get_state` は今のページのキャッシュをそのまま返すだけ。絞り込みを手で書かなくてよくなり、`page-state.ts` も消して `ai.tsx` の数行にした
    * 初めは名前を表示中の言語の 1 つにし、キーを snake_case に直す処理を残していたが、なくても困らない（名前は ja / en の両方あると、英語で頼まれても探せる）ので、API の形のまま返すことにした。Qwen での結果は変わらなかった
  * 操作の Command は、画面のボタンと同じ mutation を呼ぶ
* 題材の段階として、設定〜予約（手元の state だけの 1 ページ）から、管理画面（ページが多く、API から取る）へのステップアップにする。予約などは TanStack Query にしない

## 比べた案

| 案 | 採らなかった理由 |
| --- | --- |
| 今のまま（全件を Provider に持ち、`get_state` で絞る） | 動くが、本物のサイトと形が違う。読者のサイトに足すときの「データが届くのを待つ」が見えない |
| API にし、取得は `useEffect` で書く | AI の層が「ページと同じ取得が届くのを待つ」しくみを自分で書くことになり、かえって複雑。キャッシュも共有できない |
| ネットショップ・予約も TanStack Query にする | 手元の state だけで足りる題材。段階を分けて見せる |

## API にして変わったこと

* `mark_order_shipped` の確認はいつも出す。前は「見つからない・発送済み」を手元で判定し、確認せずに断っていたが、API から取る形では手元ではわからない。確認の後に API の理由を返す
  * 確認の文言のお客さまの名前は、取ってきた注文のキャッシュから探す。なければ番号だけ（「注文 123を発送済みにします。」）
  * Qwen が一覧を開いた直後に、存在しない番号（`123`）で呼んだことがあった。名前のない確認ダイアログが出るので、人は「やめる」を押せる（確認のテストでは承認し、API が `order 123 not found` と断り、Qwen は 1026 に直した）
* `get_state` の今のページは、描画のときの URL ではなく、呼ばれたときの URL から読む。ページを移った直後に、同じ返事の中で続けて `get_state` が呼ばれると、描き直しの前の古いページを返していたため
* 読み込み中の表示・操作の API エラーの表示が画面に入った
* テストはダミーの API を待つので、管理画面のテストに 6 秒ほどかかる
