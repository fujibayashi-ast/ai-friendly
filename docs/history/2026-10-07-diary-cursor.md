# 2026-10-07 おまけ: AI の操作をカーソルの動きで見せる（日記）

#100（サブ Issue #101・#102・#103）で決めたこと。仕様は [apps/diary/docs/commands.md](../../apps/diary/docs/commands.md)。

## きっかけ

* AI が操作すると画面が一瞬で切り替わるだけで、ページ遷移・入力・ボタン押下の様子が見えない。画面だけを見ていると、AI が何をしたかわかりにくい
* 本編の 5 つに演出を足すと処理が増えてわかりにくいので、本編はそのままにし、トップに「おまけ」（遊び・実験）の区分を作って別のサイトで見せる（もう 1 つのおまけは UI なしのサイト #14。題材を検討中）

## 決めたこと

* 題材は日記。テキストエリアとボタンだけの練習台より、普通のサイトに見える方がよい（「題材のサイトは普通のサイトに見せる」）。ページ遷移・ボタン・打ち込みの見せ場が自然にそろい、本編の題材とも重ならない
* カーソルは押すふり・打ち込むふりだけをし、実際の DOM にイベントは送らない。終わってから Command が画面と同じサイトの関数を呼ぶ（結果も今までどおり AI に返せる）
* 押す先は部品の id で指す（`pointer.click("write-entry")`）。チュートリアルのツアーと同じく、サイトは部品に普通の id を付けるだけで、AI の層を参照しない。動き・押した印・打ち込みは package に持ち、Command は id を渡すかどうかで動きを付けるかを決める
  * 最初は画面に出ている名前（ボタンの文字・`aria-label`・`<label>`）で探していたが、レビューで id にした。後から層を足すのに、id を付けるくらいはよい。名前の一致を探す処理がいらず、言語の切り替えや同じ名前の部品にも左右されない
* 打ち込みは 1 文字ずつサイトの関数（`setDraftField`）に渡す。人が打つと 1 文字ごとに `onChange` が呼ばれるのと同じなので、「画面と AI は同じ関数」のまま
* カーソルの動きは `packages/assistant` に置き、チャットがツールの実行（`execute(input, { pointer })`）に渡す。Command は `run` の 2 つ目の引数で受け取り、押す先の id を指すだけ。サイトもアプリも、カーソルのために何も import しない
  * `packages/command` には `Pointer` の型と、動きなしの既定（`click` はすぐ終わる・`type` は全部まとめて渡す）だけを置く。確認フック（`confirm`）と同じく、実行する側が渡すもの
  * WebMCP は `execute` の 2 つ目に自分の client を渡すので、登録するときに入力だけを渡すように包む。WebMCP から呼ばれたときはカーソルは動かない
  * AI の返事が終わったら `Chat` がカーソルを隠す
  * 経緯: 最初は日記の中（`apps/diary/src/ai/cursor/`）に置いていた。レビューで package に出し（`@ai-friendly/assistant/cursor`）、さらに Command・アプリの import もなくしたいとなり、今の形にした
  * 使うのは日記だけで、本編の題材には付けない
* テストでは、押した順を記録するだけの `pointer` を `execute` に渡す

## 比べた案

| 案 | 採らなかった理由 |
| --- | --- |
| 本編の題材（管理画面など）に演出を足す | 処理が増えて、本編の「普通のサイトに AI を足す」がわかりにくくなる |
| テキストエリアとボタンだけの練習台 | 何のサイトかがなくなる |
| 実際の DOM にクリック・入力のイベントを送る | 人とまったく同じ動きになるが、React の入力欄や shadcn の部品にイベントを送るのは難しく、結果（だめな理由）を AI に返しにくい |
| サイトの部品に `data-ai-target` を付けて探す | 名前が「AI のため」になる。普通の id で足りる |
| 画面に出ている名前で探す（Playwright の `getByRole` / `getByLabel` と同じ） | サイトを変えずに済むが、名前の一致を探す処理が要り、同じ名前の部品が並ぶと範囲の指定も要る。おまけの題材でそこまで見せなくてよい |
| カーソルを React の state で動かす | 動きの間に何度も描き直す。DOM を直接動かす方が軽い |
| カーソルを `packages/command` に置く | `command` はチャットなしの WebMCP だけでも使う純粋なロジック。画面の演出が混ざる |
| カーソル用の package（`packages/cursor`）を作る | package が増えるわりに得るものが少ない |
| Command やアプリが `@ai-friendly/assistant/cursor` を import して使う | 動かすたびに import とつなぎが要る。チャットが渡せば、Command は押す先を指すだけで済む |
| `command` の既定の `pointer` をカーソルにする（WebMCP でも動く） | `command` に DOM の演出が入る |

## Qwen3.5 4B での結果

| 話しかけ方 | 結果 |
| --- | --- |
| 「今日は雨で家にいた。カレーを作ったって日記を書いて」→「保存して」 | `fill_entry(title, body)` で書くページへ移り、打ち込んで「保存しますか？」と聞く。「保存して」で `save_entry` まで進み、一覧の先頭に出た |
| 「晴れて散歩した日のことを書いて」→「うん」 | 同じく書いて、聞いてから保存した |
| 「今日の日記を書いて」→「仕事が忙しかった」 | 1 回目は中身を聞かずに作文して保存した。2 回目で書き直して保存した |

* 最初は `fill_entry` の英文に `call save_entry if the user wants to save it` と書いていたら、返事に「save_entry を呼び出してください」と出た（#77 と同じ）。ツール名を出さない英文にした
* 最初は日付・天気の項目もあったが、天気を聞き返さずに決める・日付を取り違えるなど、カーソルの演出と関係のないところで迷った。日記の項目をタイトルと本文だけにした
* 何があったかを聞かずに作文するのは、システムプロンプトに「先に聞く」と書いても変わらなかった（予約フォームの聞き返しと同じ限界。#78 で LLM ごとに比べる）
