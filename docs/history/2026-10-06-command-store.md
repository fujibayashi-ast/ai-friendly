# 2026-10-06 アプリの状態にセッションをつなぐ（store）

#19 で決めたこと。仕様は [docs/commands.md](../commands.md) の「アプリの状態につなぐ」。

## なぜ必要になったか

* 最初の題材（#13）は、状態の持ち主を Command のセッションにし、画面のボタンも `session.execute(…)` で設定を変えていた。そのため `useTheme` / `useI18n` がセッションに依存していた
* レビューで「普通のサイトに **足す** 形にしたい。session / Command がなくてもサイトとして成立させたい」という方針が出た
* 記事で伝えたいのも「既存のサイトに足すだけで AI から操作できる」こと。状態の持ち主はアプリのままにし、セッションはそれを読み書きするだけにした

## 決めたこと

* `createCommandSession` は `initialState`（これまでどおりセッションが持つ）か `store`（`getState` / `setState`）のどちらかを取る
* 画面の操作は Command を通さず、アプリの setter を直接呼んでよい。Command を通るのは AI の操作（と、通したい画面の操作）

## Undo / Redo の扱い

* 画面の操作は履歴に残らないので、Undo の対象は Command を通した操作（主に AI）だけになる
* AI のバッチの後に人が画面で変えていた場合、そのまま Undo するとバッチ前の状態で人の変更を上書きしてしまう。そこで、今の状態がバッチ直後の状態と違えば戻さず `state_changed` を返す
* 比較は中身で行う（React の setter を通ると参照が変わるため）
* 比較は自前で書かず dequal を使う。依存がなく数百バイトで、`Date`・`Map`・`Set` も比べられるので、状態の形に前提を置かずに済む
* 戻せなかったバッチを履歴から捨てる案もあったが、何も変えずに理由を返すほうが予測しやすいので残した

## 採らなかった案

* **人の操作も Undo できるようにする**: 画面の操作も Command を通せば可能（`initialState` で今までどおり使えばよい）。ただし Undo / Redo が要るのは編集アプリのような Command 前提のサイトで、普通のサイトにはあまりない。Command 前提で作れる人なら、記事を読めば AI 側へすぐ転用できるので、サンプルでは扱わない
* **外での変更をセッションに通知してもらう（`notify` など）**: 呼び忘れると Undo が人の変更を上書きする。読むたびに `getState()` で今の状態を見るほうが漏れがない
